## Proposed editorial briefs — not published posts

### 1. Keeping cinematic interfaces readable without WebGL
- Audience/question: product teams deciding how an interactive site should degrade on constrained devices.
- Outline: semantic HTML baseline; motion policy; poster/error behavior; on-demand rendering; keyboard and reduced-motion verification.
- Required original work: a small reproducible code example and a captured no-JS/reduced-motion/network-failure matrix. Clearly label repository demonstrations and synthetic timings.
- Sources to consult: bundled Next Server Components documentation, R3F rendering documentation, WCAG/MDN motion guidance.
- Review: technical author and owner-approved byline pending. No claims about production performance until measured on named hardware.
- Related routes after approval: proposed web development, UI/UX design; the current website study only with explicit context.

### 2. Turning an early product idea into a useful brief
- Audience/question: founders and teams unsure what to prepare before a project conversation.
- Outline: intended users and problem; existing workflow; constraints; references; decisions and open questions; what a brief cannot promise.
- Required original work: a blank practical brief template and a clearly fictional worked example, never a disguised client case.
- Review: company wording/service scope and author approval pending.
- Related route after approval: product strategy; Contact. Avoid guaranteed timelines, budgets or outcomes.

### 3. Crediting collaborative design and engineering work
- Audience/question: readers comparing a company portfolio with a founder's individual contribution.
- Outline: ownership versus contribution; delivery status versus evidence; concept labels; permission; documenting roles and source limitations.
- Required original work: a reusable attribution checklist. Any real example must have precise role and display permission.
- Review: owner and any relevant collaborators/clients pending. No candidate screenshots may be republished as proven engagements.
- Related route after approval: Work, founder profile and verified cases.

## Editorial checklist

Write actual prose/code first. Verify the author, sources, dates and related work; obtain a named review. Store the text in local TypeScript sections (or deliberately adopt MDX later). Set `publication: approved` and an approved review only after that process. Do not fill these records with SEO-only summaries or generated placeholder posts. Rebuild to publish; no scheduling backend is introduced.

Use meaningful headings, a concise description and descriptive links. Link to services only where the topic fits; link case studies only after publication/attribution permission. Avoid location pages for unverified offices, repetitive service variants, keyword stuffing and invented search volumes. Search Console/domain ownership, sitemap submission, real crawl/index behavior and field Core Web Vitals remain deployment tasks.
